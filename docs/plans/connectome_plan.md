## 1. この計画の目的と立ち位置

### 1.1 目的

ハエの脳の配線図（コネクトーム）を使って、次のことを ALife Lab の中で行えるようにする。

1. 脳全体の信号の流れをシミュレーションし、ブラウザで観察する
2. 刺激・停止の介入、巻き戻し、分岐をする
3. 「学習」を扱う。ハエ本来の匂いの記憶と、模型を本物の記録に近づける学習の両方を含む
4. 模型が本物に近づいてきたら、仮想のハエの体とつなぎ、**実時間で動き回る様子と脳の光り方を並べて見られる**ようにする（F8）
5. ハエ同士のやりとり（求愛の歌・匂い・触れ合い・群れ）を、配線図のままでどこまで再現できるか確かめる（F11）
6. **ハエの配線図をご先祖として、脳・体・やりとりを進化させる人工生命**をつくる。ハエにはなかった合図が生まれるかを調べる（F12）
7. **ハエ以外の生き物の配線図**も、同じ計算エンジン・同じ画面で扱えるようにする（S1〜S7）。特に線虫は「全部そろった小さな実験台」として早めに入れる
8. **生き物をまたいだキメラ**をつくる。例：ハエの脳でゴカイの体を泳がせる、線虫の脳にハエの記憶の回路を移植する。コンピューターの中の人工生命ならではの実験（F13）

重い計算は GPU（CUDA C++）と MuJoCo（C 言語）で行う。Python は指揮役だけにする（3.4）。

### 1.2 正直な位置づけ（最重要）

この模型は**「本物のハエの脳の代わり」ではない**。**「配線図から作った、仮説を試すための模型」**として扱う。

足りないものは次のとおり。どれも結果の解釈に影響する。

| 足りないもの | 中身 |
|---|---|
| 線の本当の強さ | 配線図からわかるのは線の本数だけ |
| 興奮か抑制か | 画像からの推定で、ときどき外れる |
| 細胞ごとの個性 | 全細胞を同じ部品として扱う |
| 電気で直接つながる線 | 画像にほぼ写らない |
| 脳全体に効く物質 | ドーパミンなどによる「気分・空腹」 |
| 経験による線の変化 | 記憶 |
| 個体差 | データは1匹分のハエの脳だけ |

結果は「この仮定なら、こうなる」という予想として記録する。裏付けの段階は既存のルールに合わせる（未確認・確認予定・試験済み・裏付けあり・裏付けなし・結論保留）。論文や実物の実験と一致したものだけを「裏付けあり」に上げる。

### 1.3 用語（この文書で使う言葉）

| 言葉 | 意味 |
|---|---|
| コネクトーム（配線図） | どの神経細胞が、どの神経細胞に、何本の線（シナプス）でつながっているかの全表 |
| 発火 | 神経細胞が「パチッ」と信号を出すこと |
| 単純な部品モデル | 入ってきた信号を水のようにためる。少しずつ漏れる。ある高さを超えたら発火して、つながった先に水を送る。論文では LIF と呼ばれる |
| 刺激・停止 | 狙った細胞を強制的に発火させる／黙らせる。実物の実験の「光遺伝学」を真似た操作 |
| キノコ体 | ハエの脳で匂いを覚える場所 |
| ドーパミン細胞 | 「ご褒美・罰」の合図を出す細胞 |
| 比較用の脳 | 線の数は同じで、つなぎ方だけをでたらめに並べ替えた脳。結果が配線のおかげかどうかを確かめるのに使う |
| 答えを隠した実験 | 正解の脳を作って隠し、少ない記録から学習でどこまで当てられるかを試す方法 |

### 2.2 扱いのルール

- **ライセンスの確認は後回しでよい。** 個人の趣味の研究で、非商用の利用のため（ユーザー判断、2026-11-21）。それでも次の2つは守る。
  - 出典（論文・データ名・版）は記録し、画面と文書に表示する。研究の作法であり、後で公開したくなったときに困らないため
  - データそのものは配布しない（Git に入れない）。ライセンスが分からないものを再配布しないため
- **データは Git に入れない。** ローカルのデータ置き場（例: `.alife/datasets/flywire_783/`）に置き、`.gitignore` 済みであることを確認する。
- **取得したファイルは SHA-256 で記録・照合する。** 実験の記録（ExperimentSpec）には「データ名・版・ハッシュ」を含め、版が違えば別の実験として扱う。
- **表形式（parquet / feather / csv）だけを読む。** Shiu らのリポジトリにある `sez_neurons.pickle` などの pickle は開かない（AGENTS.md の方針）。必要な情報は表から作り直す。
- **他人のコードは実行しない。** モデルは論文の式から自前で実装する。Brian2・FlyGym・flyvis などの外部パッケージを入れる場合は、その都度ユーザーの許可を取る。

## 3. ALife Lab への組み込み方

### 3.1 新しい実験の種類「connectome」（生き物は差し替え式）

今の他の実験（Lenia、creature など）と同じ形の「実験の種類（substrate）」として追加する。生き物ごとの違いは「種パック」（3.5）に閉じ込め、計算エンジン・介入・巻き戻し・表示・進化の仕組みは全生き物で共通にする。以下はハエの場合の例。

| 項目 | 内容 |
|---|---|
| 状態（チェックポイントに保存するもの） | 全細胞の電位と入力、休み時間の残り、届く途中の信号（遅れの待ち行列）、乱数の状態。F4 以降は変化する線の強さも保存する |
| 1 ティック | 模型の中の 1 ミリ秒（中で 0.1 ミリ秒ずつ 10 回計算する）。F1 で決定 |
| 介入 | 刺激（狙った細胞を一定の頻度で発火させる）、停止（狙った細胞の出す線をゼロにする）、罰・ご褒美の合図（ドーパミン細胞を刺激する。F4） |
| 観測（測るだけ・脳に影響しない） | 細胞の種類ごと・脳領域ごとの発火頻度、注目する細胞（例: 口を伸ばす運動の細胞 MN9）の発火、発火した細胞の数 |
| 表示 | 発火の記録図（縦が細胞、横が時間の点の図）、脳領域ごとの発火の濃さ、3D 発光表示（F2） |

### 3.2 守る区別（AGENTS.md）

- **脳の仕組み（substrate）にご褒美関数を足さない。**
  - F4 の匂いの記憶は、ハエ自身のドーパミン細胞を使う「脳の仕組み」として実装する。設定で入れる・外すを選べ、外した状態が既定。
  - 「罰を与える」操作は外からの介入として記録する。
- **外からの調整（学習・探索）は、脳の仕組みとは別の層に置く。** F3 の刺激探索、F5〜F7 の学習が該当する。今の進化・QD 探索と同じ扱いにする。
- **見た目のための表示は、結果に影響しない。**

### 3.3 再現性

- **GPU 版でも毎回ビット単位で同じ結果を出す設計にする。** 理由は次の3つ。
  - **線の本数は整数**なので、届いた信号は「本数の整数の足し算」で集める。整数の足し算は順番が変わっても結果が同じなので、GPU が並列に足しても揺れない。小数の足し算だと順番で揺れる。
  - **乱数は「番号から決まる乱数」にする。** 種・細胞番号・時刻から計算で決まるので、保存する乱数の状態がいらない。CPU でも GPU でも同じ値になる。
  - 細胞の電位の計算は、CPU 版と GPU 版で**同じ順番・同じ精度（32bit 小数）**で行う。GPU の「掛け算と足し算をまとめて計算する最適化」は切る。
- **CPU 版（NumPy）は答え合わせ用の版**とする。GPU を持たない環境のテストもこれで行う。目標は GPU 版とのビット一致。どうしても一致しない部分が残ったら、その範囲と許す誤差を文書に書く。
- F4 以降で線の強さが小数に変わる場合も、「固定小数点の整数」（例: 1/1024 本単位）で持ち、同じ性質を保つ。

### 3.4 高速化の設計（重い処理は Python で書かない）

方針は、**重い計算はすべて GPU 用の CUDA C++ と、MuJoCo（C 言語）で行う**こと。Python は「指揮者」として、始める・止める・記録する役だけを持つ。

| 部分 | 書く言語・道具 | 理由 |
|---|---|---|
| 脳の計算（14 万個の細胞、毎 0.1 ミリ秒） | **CUDA C++ の自作カーネル** | 発火した細胞の線だけを処理する「発火した分だけ計算」方式。整数の足し算で結果が揺れない |
| 呼び出しの手間を減らす | **CUDA グラフ** | 100 ステップ分（10 ミリ秒）の命令を一度に GPU へ渡す。Python から1歩ずつ呼ぶ手間がほぼ消える |
| たくさんの脳を同時に動かす | 同じ CUDA カーネルの「まとめ版」 | 配線は共有し、細胞の状態だけを脳の数だけ持つ。総当たり調査（F3）や、種を変えた比較（F6）が速くなる |
| ハエの体（1 匹・実時間表示） | **MuJoCo の C ライブラリ**（CPU） | 1 匹なら CPU で実時間以上の見込み（FlyGym 2.x の公表値は CPU で実時間の約 2 倍）。結果も毎回同じ |
| ハエの体（たくさん同時に） | **MuJoCo Warp（GPU）** | 進化・探索で数百匹を並べて動かす用。FlyGym 2.x の公表値は実時間の約 50 倍の処理量 |
| 学習（F5〜F7） | **JAX / PyTorch**（GPU） | 自動で微分できる道具が必要。中身は GPU 用に変換されて動くので Python の速さではない。学習した値は本番の CUDA エンジンに書き戻す |
| 画面 | **three.js（WebGL2）**、データはバイナリで送る | 体の姿勢（関節角 約 100 個）と、細胞の光り方（14 万個 × 1 バイト ≒ 140 KB）を毎秒 30 回送っても 4 MB/秒程度 |

**C++ で全体を書き直すか：**
- まずは「CUDA C++ のカーネル ＋ Python の指揮」で作る。
- 指揮の手間が全体の 1 割を超えると実測されたら、脳と体を往復させる部分を C++ の拡張モジュールに移す（nanobind を使う想定）。
- Rust は使わない予定。CUDA と MuJoCo の道具がそろっているのは C/C++ の側だから。
- CUDA の翻訳器（NVRTC / nvcc）と CuPy は、今の環境の gpu オプションに入っていて、追加導入はいらない。

**実測（2026-11-21、合成データでの事前確認）**

本物の配線ではなく、**同じ規模のでたらめな配線**を使った測定。細胞 139,255 個、線 1500 万本、RTX 5070 で測った。

| 条件 | 1 秒分の計算時間 | 実時間の何倍か |
|---|---|---|
| Python から 1 歩ずつ呼ぶ（平均発火 1〜6 回/秒） | 0.22〜0.29 秒 | 3.4〜4.6 倍 |
| CUDA グラフ（平均発火 1〜6 回/秒） | 0.060〜0.065 秒 | 約 16 倍 |
| CUDA グラフ（平均発火 76 回/秒の激しい状態） | 0.106 秒 | 約 9 倍 |

- GPU メモリ使用量は約 133 MB だった。
- 測定スクリプトは作業用フォルダにある（本番コードではない）。

**この測定から分かること：**
- 脳の計算そのものは、実時間より十分速くできる見込みが高い。
- 実時間で動かすときの難所は、体の物理計算と、脳と体の往復の方になる。
- 本物の配線は偏りが大きい（一部の細胞に線が集中する）ので、F1 で実データを使って測り直す。

### 3.5 種パック（生き物ごとの差し替え部品）

**共通の形式：** どの生き物のデータも、読み込み時に次の共通の表に変換する。

| 表 | 中身 |
|---|---|
| 細胞の表 | 番号、生き物名、元データの ID、種類名、領域、位置（あれば）、役割（感覚／中間／運動／その他）、細胞の型（発火する／発火しない）、出す物質（分かれば） |
| 線の表 | 送り手、受け手、本数、符号（興奮／抑制／不明）、線の種類（化学シナプス／電気で直接つながる線） |
| 出入口の表 | 感覚の入口（例: 「左の触角の匂い受容」→ どの細胞群か）、運動の出口（例: 「右前脚」→ どの細胞群か） |
| 出典 | 論文・データ名・版・ハッシュ |

**種パックが持つもの（生き物ごとに違う部分）：**

1. **読み込み器**：元データ → 共通の表
2. **細胞の模型の既定値**
   - ハエ：発火する部品
   - 線虫：**ほとんどの細胞が発火せず、電位がなめらかに変わる**ので、「発火しない部品」を使う
   - マウス：発火する部品で、興奮・抑制の細胞の種類ごとに数値を変える
3. **体の模型**（あれば）：ハエ（F8）、線虫、ハエの幼虫、ゴカイの幼生、ホヤの幼生
4. **感覚と運動のつなぎ方**：出入口の表と、体のセンサー・モーターの対応

**計算エンジンに足すもの（全生き物に効く）：**

| 機能 | 必要な生き物 | 結果が揺れないための工夫 |
|---|---|---|
| 発火しない部品（電位がなめらかに変わる） | 線虫、ゴカイの幼生など | 細胞ごとの計算なので揺れない |
| 電気で直接つながる線（ギャップ結合） | 線虫（配線図にある）、F5 の「隠した仕組み」 | 小数の足し算になるので、受け手ごとに**決まった順番で足す**（並列でも順番を固定） |
| 外からの入力の模型 | マウス視覚野・ヒト皮質（切り取られた先からの入力がない） | 番号から決まる乱数を使う |

**大きさの違い：**
- 線虫の 302 個から、マウス視覚野の約 20 万細胞・5 億本超のシナプスまで、千倍以上の差がある。
- 小さい生き物は「たくさん同時に動かす」版で何千匹も並べる。大きいものは 1 個ずつ動かす。
- マウスは線の数が多いので、F1 と同じ方法で GPU メモリと速さを測ってから扱う。

## 4. 段階ごとの計画

各段階は「計算 → サービス/API → 画面/CLI → 保存 → テスト」を一通り完成させてから次へ進む（AGENTS.md の縦割り方針）。

### F0 データ準備

- 内容
  - 2.1 のうち F0〜 の表を取得し、ハッシュを記録する
  - 読み込み器を作る（表 → 細胞の一覧、線の一覧、細胞の種類名、脳領域）
  - 「何個の細胞・何本の線・興奮と抑制の割合」の要約を出し、論文の値と照らし合わせる
- 合格条件
  - 細胞数・線の数が出典の値と一致する（違えば理由を書く）
  - 同じファイルを2回読むと同じハッシュ・同じ要約になる
- 承認が必要なこと: **データのダウンロード（約 100 MB〜1 GB）**

### F1 脳を動かす土台と、論文の再現

- 内容
  - 単純な部品モデルを論文の式から実装する。各数値は Shiu らの既定値に合わせる（休みの電位 -52 mV、発火の高さ -45 mV、漏れの速さ 20 ms、入力の減り方 5 ms、休み時間 2.2 ms、信号の遅れ 1.8 ms、線1本の強さ 0.275 mV、刺激 150 Hz）
  - 答え合わせ用の CPU 版（NumPy）を先に作り、そのあと本番の GPU 版を作る。GPU 版は CUDA C++ のカーネルと CUDA グラフで、作りは 3.4 のとおり
  - 刺激・停止の介入とチェックポイントを実装する
- 合格テスト
  1. 手作りの小さな回路（2〜3 個の細胞）で、計算結果が手計算・解析解と一致する
  2. 保存 → 復元でビット単位に同じ続きになる
  3. GPU 版と CPU 版が同じ発火の列を出す（ビット一致が目標）。GPU 版を2回動かして完全に同じになる
  4. **論文の再現**
     - 甘味の細胞を刺激すると、口を伸ばす運動の細胞（MN9）が発火する
     - 苦味を加えると抑えられる
     - 触角への刺激で毛づくろいの細胞が動く
     - などの、論文に出てくる確認項目を並べる
  5. **比較用の脳では 4 の反応が出ない（または弱い）。** 配線のおかげであることの確認
- 記録
  - 再現度レポート（`docs/reference_fidelity/connectome_fly.md`）に、項目ごとの一致・不一致を書く
  - 2026 年の追試では、論文の13項目のうち完全再現が8、一部再現が3、再現できなかったのが2。全項目は一致しない前提で、不一致も消さずに残す
- 測ること: 1 秒分の計算にかかる時間（CPU / GPU / CUDA グラフあり・なし）、メモリ使用量、同時に動かせる脳の数

### F4 匂いの記憶（ハエ本来の学習）

- 内容
  - キノコ体の「匂いを表す細胞 → 出口の細胞」の線だけを可変にする（匂いを表す細胞は約 5 千個）
  - ドーパミン細胞が発火した前後に、使われていた線を弱める（または強める）ルールを入れる
  - ルールの形と強さは、文献を F4 着手時に調べて決める。**簡略化した推測であることを明記する**
- 実験（パブロフの犬型）
  1. 匂いA と罰の合図を同時に数回与える → 匂いA だけで「逃げる」出口の細胞が強く反応するか
  2. 匂いB は変わらないか（覚えたのは匂いA だけか）
  3. 回数を増やすと強くなるか
  4. 罰なしで匂いA を繰り返すと戻るか（忘れる）
- 比較用
  - 匂いと罰を時間をずらして与える → 覚えないはず
  - ドーパミン細胞を停止する → 覚えないはず
  - 比較用の脳 → 結果を比べる
- 画面
  - 「訓練前の脳」と「訓練後の脳」を分岐で並べて比べる
  - 変化した線を表示する
- 参考：arXiv 2611.09930（全脳モデルで「狙った匂いだけ・繰り返すほど・元に戻せる」学習を扱った論文。中身は着手時に精読）

### F5 答えを隠した実験（学習で本物に近づけられるかの検証）

- 内容
  1. 「正解の脳」を作り、答えを隠す。今の模型に無い仕組みを足したもので、例えば次のような仕組みを想定する
     - 電気で直接つながる線
     - 種類ごとに違う反応の速さ
     - 一部の興奮・抑制の取り違え
     - 脳全体に効く物質による感度の変化
  2. 正解の脳から、**本物の実験と同じくらい限られた記録**を取る。条件は次のとおり
     - 一部の細胞だけを記録する
     - 時間的に粗い記録にする
     - 雑音を入れる
  3. 仕組みの欠けた模型を、記録に合うように学習させる。学習は外の層に置き、JAX または PyTorch の自動微分を使う。発火は微分できないので、近似の微分か、発火頻度で考える模型を使う
  4. 次の3点を測る
     - どこまで正解に戻せるか
     - まだ見せていない刺激への反応を当てられるか
     - 記録の量・どの細胞を記録するかで、結果がどう変わるか
- 比較用：でたらめ配線から学習した場合、学習しない場合
- 範囲：まず匂いの回路など一部分（約 1 万個）から始める。全脳はメモリの見積もりを見て判断（7章）
- 期待される成果
  - 「記録がどれくらいあれば隠れた仕組みを当てられるか」
  - 「どの細胞を記録すると効くか」の地図
  - 同じ記録に合う答えが複数ある場合は、その事実を記録する。これも重要な結果として扱う

### F8 実時間で動くハエ（脳 → 体、体 → 脳）

**ねらい：** 脳の模型が本物に近づいてきた段階で、**仮想のハエが画面の中で実時間に動き回る様子**を見られるようにする。行動の例は、歩く、向きを変える、餌に口を伸ばす、触角をこする、匂いから逃げる、など。同時に、そのとき脳のどこが光っているかを並べて表示する。

#### 全体のつながり

```
 [環境]  餌・匂いの流れ・光・障害物
   │ 感覚（体のセンサー → 感覚の細胞の発火の速さ）
   ▼
 [脳] GPU・CUDA C++   14 万個の細胞     ←── 画面から刺激・停止もできる
   │ 脳から体への指令を送る細胞（数百〜千個程度）の発火
   ▼
 [指令の読み取り]  前進／旋回／後退／毛づくろい／口を伸ばす／飛び立つ
   ▼
 [脚の動きを作る部分]  レベル1：手書きの歩き方の型 ／ レベル2：脊髄に相当する部分の配線図
   ▼
 [体] MuJoCo（関節・筋肉の代わりのモーター・脚の吸着・地面との接触）
   │ 体の状態（姿勢・脚の接地・位置）
   └──→ 感覚へ戻る（ぐるっと一周）
```

#### 体の模型

- **第一候補は NeuroMechFly の体のデータ**（実物のハエを CT で撮影して作ったもの。Apache-2.0）。
  - 使うのは体のデータ（MuJoCo 用の設定ファイルと形のデータ）だけで、FlyGym のプログラム自体は使わない。
  - それでも外部データの取得になるので、承認が必要。
- 承認が得られない場合は、今の creature の作り方で簡略化したハエ（頭・胸・腹、6本脚 × 5関節、触角・口）を自作する。

#### 脳と体のつなぎ方（2段階）

| レベル | 脚の動きを作るもの | 分かること・限界 |
|---|---|---|
| **レベル1** | 脳の指令（前進・旋回など）を、**手書きの歩き方の型**に渡す。型は NeuroMechFly v2 論文の方式（脚ごとのリズム ＋ 足を引っかけたときの反射）を自前で実装する | 「脳の判断で行動が切り替わる」様子は見られる。ただし**脚のリズムそのものは手書き**。画面にもそう明記する |
| **レベル2** | **脊髄に相当する部分（腹側神経索）の配線図**（BANC または MaleCNS）を脳とつなげて動かし、脚の運動の細胞 → 筋肉の代わりのモーターへ流す | 「配線図だけから歩くリズムが生まれるか」という研究上の問いになる。そのままでは歩けない可能性が高い。F5〜F7 の方法（学習で本物に近づける）で調整する。ここが「本物に近づいたら」の本丸 |

#### 感覚の入れ方

| 感覚 | 体側で計算するもの | 脳側の入口 |
|---|---|---|
| 味 | 脚先・口が餌の場所に触れているか | 味を感じる細胞（甘味・苦味など） |
| 匂い | 左右の触角の位置での匂いの濃さ。匂いの流れは今の格子の仕組み（拡散）で計算できる | 匂いの受容細胞（種類ごと） |
| 視覚 | 複眼の向きごとの明るさ（GPU で描画して縮める） | 目の入口の細胞（FlyWire は目の部分も含む） |
| 触覚 | 触角に何かが当たったか | 触角の機械感覚の細胞（毛づくろいの引き金） |
| 体の状態 | 関節角・接地（レベル2のみ） | 脊髄から脳へ上がる細胞 |

#### 実時間の作り方

| 項目 | 内容 |
|---|---|
| 時刻合わせ | 脳も体も 0.1 ミリ秒刻みで計算し、1 ミリ秒ごとに指令と感覚を受け渡す |
| 計算の配置 | 脳は GPU（CUDA グラフで 1 ミリ秒分ずつ）、体は CPU の MuJoCo。両者を並行に走らせ、受け渡しの量は数 KB に抑える |
| 実時間に間に合わないとき | 画面に「実時間の 0.5 倍」のように**正直に表示**して、スローモーションで見せる。科学的な状態は飛ばさない（画面のコマだけは落としてよい） |
| 目標の速さ | 脳＋体＋表示で実時間の 1 倍以上、画面は毎秒 30〜60 コマ（F8 で実測して確定） |

#### 画面（分かりやすさの工夫）

- **左右の2画面**
  - 左：アリーナの中のハエ。3D で、餌・匂いの流れ・足あとを表示する
  - 右：脳の 3D 発光表示
  - 全画面表示にも対応する
- **「今の指令」メーター**：前進・旋回・毛づくろい・口を伸ばす、の強さを棒で表示する。「脳が今どの行動を選んでいるか」が一目で分かるようにする
- **クリックで対応を見る**
  - 脳の細胞をクリックすると、それがどの指令・どの体の部位につながるかを示す
  - 体の部位をクリックすると、その部位に関わる細胞が脳の中で光る
- **その場で手を加える**
  - 餌や匂いの元を置く、ハエをつつく、明かりを消す
  - 特定の細胞群を刺激・停止する（例: 「口を伸ばす細胞を止めると、餌の上でも食べない」をその場で見る）
- **記録と巻き戻し**：脳と体の両方をチェックポイントに保存し、巻き戻し・分岐ができる。MuJoCo を CPU で 1 本で動かす場合は毎回同じ結果になる

#### 合格条件

- 決めた場面を再生して、同じ行動が再現される。場面の例：
  - 餌に近づくと止まって口を伸ばす
  - 触角に触れると毛づくろいする
  - 苦い餌では食べない
- 比較用の脳（でたらめ配線）や、指令の細胞を停止した脳では、その行動が崩れる
- 計測を記録する：実時間の何倍か、画面のコマ数、各部分（脳・体・受け渡し・描画）の時間の内訳

#### 正直な注意

- レベル1 の歩き方は手書きなので、「脳だけで歩いている」とは言わない。
- 行動が見えても、それは「この模型と、この読み取り方なら、こう動く」という結果であって、本物のハエと同じ理由で動いている保証はない。
- 2026年3月の Eon Systems の発表に批判が出たのも、この区別が曖昧だったため。

### F11 ハエ同士のやりとり（生まれつきのコミュニケーション）

**ねらい：** 配線図のまま（学習・進化なし）で、ハエ同士のやりとりがどこまで再現できるかを確かめる。F12 の「出発点」にもなる。

#### 使う配線図

- メス：FlyWire（脳）、BANC（脳＋脊髄に相当する部分）
- オス：MaleCNS（脳＋脊髄に相当する部分）
- オスにしかない細胞（求愛の命令を出す P1 など）があるので、**オスとメスで違う脳を入れたハエ**を同じ場に置く

#### やりとりの通り道（環境側で計算するもの）

| 通り道 | 送る側 | 伝わり方 | 受け取る側 |
|---|---|---|---|
| 音（求愛の歌） | 羽を震わせる（脊髄側の歌の回路 → 羽のモーター） | 距離とともに急に弱まる空気の揺れ。数ミリしか届かない | 触角の音を聞く細胞 |
| 匂い・フェロモン | 体の表面の匂い。種類はオス・メスで固定 | 格子の上で広がる場（今の「広がる場」の仕組みを流用） | 匂いの受容細胞、脚先の味の細胞（触れたとき） |
| 見た目 | 体の位置・羽を広げる姿勢 | 各ハエの目の向きで景色を描画（F8 の視覚） | 目の入口の細胞 |
| 触れ合い | 脚・体の接触 | MuJoCo の接触判定 | 脚の触覚の細胞 |

#### 3段階

| 段階 | 内容 | 前提 |
|---|---|---|
| ① 脳だけでつなぐ | オスの脳の歌の細胞の発火を音に変え、メスの脳の音を聞く細胞へ入れる。体なしで、メスの脳のどこが反応するかを調べる | F1（MaleCNS の読み込みを含む）。脳2つ分なので軽い |
| ② 体ありの2匹 | オスが目でメスを追い、触れて味見し、歌う。メスは歩みを遅くするか、離れる | F8 レベル2（羽と脚を脊髄側の配線図から動かす） |
| ③ 群れ（10〜100匹） | 群れで嫌な匂いを避ける実験の再現（Ramdya ら 2015：数が増えるほどよく避け、原因は脚の触れ合い）。オス同士のけんか | F9 |

#### 合格テスト（答え合わせ）

- オスの P1 細胞を刺激すると、追いかけや羽を広げる動作が出るか（実物の実験で知られている反応）
- 歌の回路（少なくとも8種類の細胞）を一つずつ止めると、歌のどの部分が消えるか。Janelia の結果と比べる
- 群れの大きさを変えたとき、匂いを避ける時間が増えるか。脚の触覚の細胞を止めると、その効果が消えるか
- 比較用：でたらめ配線の脳、やりとりの通り道を一つずつ塞いだ場合

#### 注意

- 求愛は年齢・交尾の経験・空腹や、脳全体に効く物質に強く左右される。この模型にはそれらが入っていないので、一部の場面しか再現できない可能性が高い。再現できなかった項目も記録する。

### F12 ハエから始まる人工生命（脳・体・やりとりの進化）

**ねらい：** 本物のハエの配線図を「ご先祖」にして、コンピューターの中で世代を重ねさせる。その中で次のことが起きるかを見る。

- 脳の配線が変わっていく
- 体の形が変わっていく
- **ハエにはなかった新しい合図（コミュニケーション）が生まれる**

ここから先は「ハエの再現」ではなく、**ハエを出発点にした人工生命**として扱う。画面と記録で、本物のハエからどれだけ離れたかを常に示す。

#### 何を受け継がせるか（遺伝子の設計）

1匹ごとに 1500 万本の線をまるごと持たせると、メモリも探索も重すぎる。そこで次のように持つ。

**「共通のご先祖の配線図 ＋ 1匹ごとの小さな差分」**

| 遺伝子の部分 | 中身 | 変わり方（突然変異） |
|---|---|---|
| 細胞の種類ごとのつまみ | 発火しやすさ、反応の速さ、出す信号の強さ | 少しずつ増減 |
| 種類どうしの線の倍率 | 「種類A → 種類B」の線全体の強さを何倍にするか | 少しずつ増減、まれに興奮と抑制が入れ替わる |
| 新しい線（構造の変化） | ご先祖にはない「種類A → 種類B」のつながり | まれに追加・削除 |
| 細胞の種類の複製 | ある種類の細胞群をまるごと複製し、別々に変わっていけるようにする（生物の遺伝子重複に似た仕組み） | ごくまれ |
| 体の形 | 脚の長さ・太さ、羽の大きさ、触角の長さ、体の重さ。後には脚の本数も | 少しずつ増減 |
| 合図の出し方（新設） | 羽の震わせ方（音の高さ・リズム）、出す匂いの種類と量、見せる姿勢 | 少しずつ増減 |
| 学習のしかた | F4 の学習ルールの強さ。生きている間に覚える力 | 少しずつ増減 |

**この持ち方の利点：**
- ご先祖の配線は GPU に 1 つだけ置いて全員で共有し、差分は小さな表で持つ。そのため 3.4 の「たくさんの脳を同時に動かす」仕組みがそのまま使える。
- **「ハエらしさ」を数で示せる。** ご先祖からの差分の大きさ（変わった線の割合、増えた細胞の種類、体の形の差）を、「ハエからの距離」として系統図と画面に表示する。

**体が変わったときの、脳とのつなぎ方：**
- 脚の数が変わったら、その脚を動かす細胞群を複製または削除して対応させる。
- まずは長さ・大きさなどの連続的な変化から始める。脚の本数のような段差のある変化は後回しにする。
- 今の creature の「体と動きの共進化」（ADR 0031）の仕組みを流用する。

#### 世代の回し方（2つの方式）

| 方式 | 内容 | 向いていること |
|---|---|---|
| **A. 世代ごとの選抜** | 決めた課題（餌集め、捕食者から逃げる、など）の成績で親を選ぶ。今の探索・QD の仕組みを流用 | 条件をそろえた比較実験。「どの環境なら合図が生まれるか」を調べる |
| **B. 世界の中で生まれて死ぬ** | 餌を食べて体力をためる。オスとメスが出会って子を産み、子は両親の遺伝子を混ぜて受け継ぐ。体力が尽きたら死ぬ。成績の点数はない（今の agent_world と同じ考え方） | 「人工生命らしさ」が最も高い。予想していなかった進化が起きやすい |

方式 B は新しい実験の種類「fly_world」とする。決まった成績の点数は持たず、生き残りと子孫の数だけが自然に選抜を生む（AGENTS.md の区別を守る）。

#### 新しい合図が生まれやすい環境（実験条件）

過去の人工生命研究（ロボットや仮想生物の進化）で、合図が生まれやすいと言われてきた条件を、比べられるように用意する。

| 条件 | 合図が役立つ理由 |
|---|---|
| 散らばった餌場 | 見つけた個体が知らせると仲間が得をする |
| 捕食者（上から迫る影） | 危険を知らせる合図 |
| オスとメスの出会いが必要 | 相手を見つけ、選ぶための合図（求愛の発展） |
| 血縁が近い集団か、ばらばらか | 血縁が近いほど正直な合図が生まれやすい、という過去の報告がある。その確認 |
| 合図を出すのに体力を使うか | 合図の「値段」で、うそ・正直がどう変わるか |

#### 「合図が生まれた」と言うための基準（比較用の実験つき）

見た目で「やりとりしているっぽい」だけでは言わない。次の3つがそろったときに「試験済み」とする。

1. **合図に意味がある。** 合図の出し方と送り手の状況（餌を見つけた、危険が来た）の関係が、偶然の範囲より強い。合図を個体間でシャッフルした比較用と比べる
2. **受け手が反応する。** 合図を受けた個体の行動が変わる。合図を消した世界の録画と比べる
3. **役に立っている。** 途中から合図の通り道を塞ぐ（分岐して介入）と、その集団の生き残りや餌集めが下がる

あわせて、次を記録する。
- 複数の種（10 本程度）で何本に生まれたか
- 生まれた合図が、ご先祖のハエの合図（歌など）を作り変えたものか、まったく新しいものか

#### 計算の重さと、明示的な「解像度」の選択

数十〜数百匹を何千世代も回すには、1匹ずつ 14 万個の細胞と精密な体を毎回計算するのは重すぎる見込み。そこで次の2つを**設定で明示的に選べる**ようにする。黙って小さくすることはしない（AGENTS.md）。

| 選択 | 細かい版 | 軽い版 |
|---|---|---|
| 脳 | 細胞 1 個ずつの全脳（14 万個） | **細胞の種類ごとにまとめた脳**（約 8 千の種類を 1 単位ずつ、発火の速さで計算） |
| 体 | MuJoCo の精密な体 | 平面上を動く簡易な体（脚の接地は簡略化） |

- 軽い版と細かい版がどこまで同じ振る舞いをするかは、F1・F3 の合格テストで比べ、一致度を文書に書く。
- 進化は軽い版で回し、**気になる個体だけを細かい版で再生して詳しく見る**、という使い方を基本にする。
- 細かい版で再生した結果が軽い版と食い違ったら、その事実も記録する。

#### 画面

- 世界全体の俯瞰（ハエの群れ、餌、匂いの場、合図が出た瞬間を色で表示）
- 系統図（今の系統図を流用し、「ハエからの距離」で色分け）
- 1匹を選んで、その脳の 3D 発光表示と、体の詳しい動きを見る（細かい版で再生）
- 合図の辞書：生まれた合図ごとに「どんな状況で出て、受け手がどう反応したか」をまとめた表

### S1〜S7 ハエ以外の生き物

どれも「種パック」（3.5）を1つ足す作業になる。共通の流れは次のとおり。

**読み込み → 要約を論文の値と照合 → 発火・反応の基準テスト → 3D 発光表示 → （体があれば）体とつなぐ**

| 段階 | 生き物 | やること | 答え合わせ・見どころ | 入れる時期 |
|---|---|---|---|---|
| **S1** | **線虫** | 発火しない部品とギャップ結合を実装する。全身の配線図に、自作の体（筋肉の列が波打って進む細長い体。MuJoCo または平面の簡易体）をつなぐ | 前に這う・後ずさりする・触れたら逃げる反応。本物の全細胞活動記録との比較（記録データの入手は要確認）。**F5〜F7 の学習の方法を、ハエより先にここで試す** | **F1 の直後**（エンジンが種パック式で動くことの最初の確認も兼ねる） |
| S2 | ハエの幼虫 | 脳の配線図 ＋ 這う体 | 匂いに近づく・記憶（キノコ体がある）。成虫のハエ（F4）との比較 | F4 の後 |
| S3 | ゴカイの幼生 | 全身の配線図（筋肉・泳ぐための毛の細胞を含む）＋ 泳ぐ体（水の抵抗は簡略化） | 光に向かって泳ぐ行動など。体の動かし方まで配線図だけで決まるか | S1 の後 |
| S4 | ホヤの幼生 | 小さな中枢 ＋ おたまじゃくし形の体 | 光・重力への反応。入門用の見本 | S1 の後（軽い） |
| **S5** | **マウス視覚野** | 1 mm³ の配線図 ＋ 興奮・抑制の部品 ＋ 視覚の入力の模型 | **同じ組織の約 7.5 万個の活動記録に合わせる**（F7 の本番）。映画を見せたときの反応を当てられるか。似た反応の細胞どうしがつながりやすいという報告の再確認 | F5 の後 |
| S6 | ヒト大脳皮質 | 1 mm³ の配線図の 3D 表示と統計。シミュレーションは「切り取られた断片」と明記して試す程度 | 3D で眺める、マウスの皮質と配線の統計を比べる | 随時（軽い） |
| S7 | ゼブラフィッシュの幼魚 | 公開されたら種パックを作る。背骨のある動物で初の全脳 ＋ 泳ぐ体 | 全脳の活動記録が得意な動物なので、F7 の方法がそのまま使える見込み | 公開待ち |

**生き物どうしの比較もできる。** 同じ統計（線の密度、つながりの偏り、ループの数など）と同じ実験（比較用の脳との差など）を全生き物にかけて並べる。「小さな脳と大きな脳で何が違うか」を同じ物差しで見る。

### F13 キメラ（生き物をまたいだ人工生命）

**ねらい：** 違う生き物の配線図や体を組み合わせる。コンピューターの中でしかできない人工生命の実験。

#### 組み合わせの4つの型

| 型 | 例 | 難しいところ |
|---|---|---|
| **① 脳の移植** | ハエの脳でゴカイの体を泳がせる。線虫の脳でハエの体を歩かせる | 元の脳の出口（「右前脚」など）と、新しい体の入口が合わない。**つなぎの層**が必要 |
| **② 回路の移植** | 線虫の脳に、ハエの匂いの記憶の回路（キノコ体）を足す。ハエの幼虫に成虫の視覚の回路を足す | 移植した回路の入口・出口を、受け入れ側のどの細胞につなぐか |
| **③ 脳の合体** | ハエの脳と線虫の脳を並べ、少数の線で橋渡しする | 橋渡しの線の選び方 |
| **④ 同じ種の交配** | FlyWire（メス）と MaleCNS（オス）のハエどうし、線虫の個体どうし | 細胞の種類名で対応が取れるので、生物学的に意味のある交ぜ方ができる（F12 の交配にそのまま使える） |

#### 仕組み：部品と差し込み口

- 生き物の配線図を、**入口と出口の付いた部品**として扱う。入口・出口は「出入口の表」（3.5）で定義する。
- 部品どうしは**つなぎの層**で結ぶ。つなぎの層は、出口の細胞群から入口の細胞群への少数の線。
- つなぎの層の線の強さ（と、必要なら線の有無）は、外から調整する。調整には F12 の進化か、F6 の学習を使う。
- 移植された部品の中身は、最初はそのまま固定する。進化の段階で、F12 と同じ「差分の遺伝子」で変われるようにする。

#### 見せ方・測り方

- **由来の内訳**を表示する。例：「ハエ 82%・線虫 3%・つなぎの層 15%」。系統図と 3D 表示で、由来ごとに色分けする。
- 次のように問いを立てて比べる。
  - 「ハエの脳 ＋ ゴカイの体は、ゴカイ本来の脳より上手に泳げるようになるか」
  - 「キノコ体を移植した線虫は、匂いを覚えるようになるか」
- 比較用：
  - つなぎの層だけを学習させた場合と、でたらめ配線の部品に同じことをした場合
  - 移植した回路を停止した場合

#### 段階

| 段階 | 内容 | 前提 |
|---|---|---|
| F13a | ④ 同じ種の交配（ハエのオス・メス、線虫の個体） | F12a、S1 |
| F13b | ① 脳の移植（小さい組み合わせから：線虫の脳 ↔ ハエの幼虫の体など） | S1、S2、F12a |
| F13c | ② 回路の移植（キノコ体 → 線虫など） | F4、S1 |
| F13d | ③ 脳の合体、大きな組み合わせ（ハエの脳 ＋ ゴカイの体など） | F8、S3 |

#### 注意

- キメラは本物の生き物のモデルではない。「部品の組み合わせで何が起きるか」という人工生命の実験として扱い、生物についての主張にはしない。
- 部品の大きさが大きく違う場合（ハエ 14 万個 ＋ 線虫 302 個）、つなぎの層の設計で結果が大きく変わる。設計の選び方も記録して比べる。

## 5. 正しさの確かめ方（まとめ）

| 種類 | 中身 |
|---|---|
| 基準テスト | 小さな回路の手計算一致、保存・復元のビット一致、CPU 版と GPU 版の統計一致 |

| 裏付けの段階 | 未確認 → 確認予定 → 試験済み → 裏付けあり／裏付けなし／結論保留 |

## 6. 安全・データの方針

- 他人のコードは実行しない（自前実装）。pickle は開かない
- 外部パッケージ・外部データ（Brian2, MuJoCo Warp, flyvis, NeuroMechFly の体のデータなど）は、導入前にその都度承認を取る
- データ・実行結果・チェックポイントは Git に入れない。コミット前に `scripts/check_staged.py` で確認する
- ライセンスの確認は後回し（個人の趣味の研究）。出典は表示し、データは再配布しない
- 計算・ディスクの上限を設定に持たせる（例: データ置き場の上限、学習の時間上限）
- GPU の計算機能を外部に公開しない（今までどおり 127.0.0.1 のみ）

## 8. リスクと未解決の問い

| リスク・問い | 対応 |
|---|---|
| 後で結果を公開したくなる | そのときに各データのライセンスを確認する。出典は最初から記録しておく |
| 大きなデータ（MICrONS など）の取得に時間・容量がかかる | 必要な表だけを取る。データ置き場に容量の上限を設ける |
| 生き物ごとに細胞の性質が違う（線虫は発火しない、など） | 種パックごとに細胞の模型の既定値を持ち、基準テストを分ける |
| キメラのつなぎ方で結果が大きく変わる | つなぎ方の設計自体を比較の対象にして記録する |
| 論文の結果が一部再現しない | 不一致も記録する。原因（版の違い、数値の違い）を調べて書く |
| GPU の結果が毎回わずかに揺れる | 整数で足し合わせる設計で防ぐ（3.3）。それでも残る部分は CPU 版との差の範囲を文書に書く |
| 本物の配線は偏りが大きく、合成データより遅い | F1 で実測する。線の多い細胞は別の処理に分ける、などの工夫を用意しておく |
| 体と脳の往復で実時間に届かない | 時間の内訳を測る。遅いところを C++ に移す。それでも届かなければスローモーションと明記して表示する |
| 体の接触計算が重い（0.1 ミリ秒刻み・細かい形） | 接触には簡単な形（カプセル）を使い、細かい形は表示だけに使う |
| 脊髄の配線図から歩くリズムが出ない（レベル2） | それ自体を結果として記録する。学習で調整し、手書きの型（レベル1）と比べる（**2026-11-23 決着・F8 完結：BANC v888 / MaleCNS v1.0 で 16 発生系統 ALIF 学習により純 MuJoCo 前進 `+1.41 cm / +0.90 cm`・直進安定性 37〜44 倍・雌雄間ゼロショット転移を達成。続く事前登録「ラチェット封印＋交連分離・反位相白黒テスト」では、隔離実 VNC 配線のみが反位相 3 脚振動 `tripod_corr = -0.435 / -0.936` を創発した（同予算シャッフルは `+0.996/+0.997` 同期固定＆全中枢完全静止）一方、全中枢での持続的反位相前進歩行は未達（E3 陰性結果）と確定し、非発火・ギャップ結合を要する構造的境界として `docs/reference_fidelity/connectome_fly.md`・ADR 0045 に記録**） |
| 種類ごとにまとめた軽い脳が、全脳と違う振る舞いをする | 一致度を測って文書化する。気になる結果は全脳で再生して確かめる |
| 進化で新しい合図が生まれない | 条件（餌場・捕食者・血縁・合図の値段）を変えて比べる。生まれなかったことも結果として記録する |
| 進化が「ずる」を見つける（物理計算の穴を使って動くなど） | 体の動きの物理的な妥当さを検査する。怪しい個体は細かい版で再生して確かめる |
| 学習で本物に近づいたように見えても、中身が同じとは限らない | 見せていない実験での予測精度で判断する。同じ記録に合う答えが複数ある場合は、その事実を明記する |
| 細胞の位置・種類名の表の入手方法 | F0 で確認する。なければ脳領域単位の表示にする |
| 匂いの記憶のルールの選び方 | F4 着手時に文献を調べる。ルール違いを比較できるようにする |
| 派手な表現による誤解（「脳を再現」など） | 画面・文書・README で「仮説を試す模型」と明記する |
